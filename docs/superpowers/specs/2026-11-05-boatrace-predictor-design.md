# ボートレース予想アプリ 設計書

- 作成日: 2026-11-05
- 利用者: 本人のみ（個人利用・配布しない）
- 実行環境: Windows PC（第1段階）。後でクラウドへ移す前提

## 1. 目的

指定した場で行われるレースを監視し、次の3つの観点で予想する。条件を満たしたら「買いシグナル」を出す。

1. **本命予想**: 的中確率が高い（堅い）レース・買い目を見つける
2. **オッズ判断**: 期待値（的中確率 × オッズ）から買いかどうかを判定する
3. **展開予想**: 逃げ / 差し / まくり / まくり差し などの展開シナリオの確率を推定する

対象は全国24場すべてとし、監視する場はコマンドで指定する（複数場の同時監視も可）。場ごとに傾向が違うため、ルールとモデルの補正は場別に持つ。

狙いは **回収率と的中率の両方** とする。最大の特徴は、利用者本人の経験則（自分ルール）を組み込み、結果から学習して進化する **自分専用** の予想にすること。

### 成功の基準

- 当日のレースについて、締切前に的中確率・期待値・シグナルと、その根拠（該当ルール）を表示できる
- 利用者の買い目（例: `1-456-全`）の的中確率・合成オッズ・期待値を評価できる
- 過去データで、ルールを入れた場合と外した場合の的中率・回収率を比較できる
- 利用者の予想と結果を記録し、ルールごとの答え合わせと修正候補を自動で出せる
- 結果が蓄積されるほど、ルールの強さ・確率の精度（キャリブレーション）・利用者とアプリの統合比率が更新され、的中率・回収率が上がっていく

### 対象外（現時点）

- 自動投票（実装しない）
- 通知（LINE / Slack / メール等）。シグナルは画面表示とCSVに出す。後から追加できる構造にはする
- 配布用インストーラーやストア公開
- スマホ向け画面（第2段階以降で検討）

## 2. データ取得元

| 区分 | サイト | 用途 |
|---|---|---|
| 主 | 公式サイト `https://www.boatrace.jp/owpc/pc/race/index` | 出走表（級別、全国・当地勝率、モーター・ボートの2連対率）、直前情報（展示タイム、スタート展示、進入、チルト、風、波）、3連単などのオッズ、結果（着順・決まり手・払戻金）、選手のコース別成績 |
| 補助 | ボートフロンティア `https://boatfrontier.jp/` | 場別×コース別成績など、公式サイトでは見づらい選手傾向データ |

### 取得の決まり

- アクセスは最小限にする。リクエストの間隔は1秒以上空け、取得したページはキャッシュする
- 実装に入る前に、各サイトの利用規約と robots.txt を確認する。自動取得が禁止されているページや会員限定ページは取得しない
- ボートフロンティアのデータは「あれば使う」扱いにする。取得できなくても公式データだけで全機能が動くこと
- 取得処理はサイトごとに部品を分け、ページ構造が変わっても該当部品の修正だけで済むようにする

### 未確認事項（実装の最初の段階で解決する）

- 開発に使うクラウド環境では、両サイトへの接続がネットワーク設定でまだ許可されていない。実際のページ構造と利用規約は、許可後または利用者のWindows PC上で確認する
- ボートフロンティアで取得できる具体的な項目と、利用規約上の可否

## 3. 全体構成とデータの流れ

```
[公式サイト / ボートフロンティア]
        │ ① 収集 (collector)
        ▼
   SQLite (race.db)   レース・選手・直前情報・オッズ・結果
        │
        ▼ ② ベース確率 (model)
   6艇の1着確率 → 3連単120通りの確率
        │
        ▼ ③ 展開補正 (scenario)
   逃げ / 差し / まくり / まくり差し / その他 の確率で着順分布を組み直す
        │
        ▼ ④ 自分ルール補正 (rules)   rules/common.yaml, rules/<場>.yaml
        │
        ▼ ⑤ 判定 (signal)
   的中確率・オッズ・期待値 → 🟢堅い / 🟡妙味 / ⚪見送り
        │
        ▼ ⑥ 出力
   画面表示（該当ルール・確率の変化つき）＋ signals.csv
```

言語は Python、データベースは SQLite を使う。

### 部品

| 部品 | 役割 | 入力 → 出力 |
|---|---|---|
| `collector` | サイト別にデータを取得してDBに保存する。アクセス間隔の制御とキャッシュを担う | URL → DB |
| `model` | 統計ベースで各艇の1着確率を出し、3連単120通りの確率に展開する | 出走表・直前情報 → 確率 |
| `scenario` | 展開シナリオごとの着順分布を出す。「3がまくる → 4が展開をもらう → 5・6がまくり差しで入る」のような連鎖を表現する | 確率・進入・展示 → 3連単の確率 |
| `rules` | YAMLのルールを読み込み、条件に当てはまれば補正する | 確率 → 補正後の確率と該当ルール一覧 |
| `signal` | 合成オッズ・期待値を計算し、シグナルを判定する | 確率・オッズ → シグナル |
| `backtest` | 過去レースで成績を計算し、ルールの有無で比較する | DB → 成績レポート |
| `journal` | 利用者の予想（買い目・根拠ルール・自信度・メモ）を記録する | 入力 → DB |
| `review` | 結果との答え合わせ、ルールごとの判定、修正候補の作成を行う | 予想・結果 → 振り返り |
| `learning` | モデルの再学習、ルールの強さの学習、統合比率の学習、しきい値とルール候補の提案を行う | DB → 更新された重み・提案 |
| `cli` | コマンドの入口 | — |

### コマンド

| コマンド | 内容 |
|---|---|
| `boat watch 住之江 桐生 ...` | 指定した場（複数可、`all` で開催中の全場）の当日の全レースについて、締切10分前・5分前・2分前に取得と判定を行い、画面に表示する |
| `boat predict 住之江 12R` | 1レースの現時点の予想を表示する |
| `boat check 住之江 12R "1-456-全"` | 自分の買い目の的中確率・合成オッズ・期待値を評価する |
| `boat backtest [--rules on/off]` | 過去データで成績を計算する |
| `boat rules report` | ルールごとの成績表を表示する |
| `boat bet 住之江 1R "1-456-全" --rules ... --confidence 4` | 自分の予想を記録する（5.1） |
| `boat review 住之江 1R` | 結果との答え合わせ・ルールごとの判定・修正候補を表示する（5.2） |
| `boat report me` | 自分の得意・不得意と、自分／アプリ／統合の成績比較を表示する（5.4） |
| `boat learn` | モデル・ルールの強さ・統合比率を再学習する（5.5） |
| `boat memo 住之江 12R "..."` | 振り返りメモを保存する |
| `boat collect --from YYYY-MM-DD --to YYYY-MM-DD` | 過去データを少しずつ収集する |

表示例:

```
住之江 12R  締切5分前
買い目 1-4-全 (4点)  合成オッズ 4.2倍  的中確率 33%  期待値 1.25(安全率込み)  🟡妙味
展開: 逃げ 68% / まくり差し 14% / まくり 10% / 差し 3% / その他 5%
該当ルール: R1(逃げ↑強) R2(逃げ↑中) R3(差し↓強) R8(4号艇↑中)
```

### エラー時の扱い

- 取得に失敗した、または必要な項目が欠けている場合、そのレースは「判定不可」と表示する。推測値では埋めない
- 補助サイトが取得できない場合は、そのデータを使うルールを「データなしのため判定対象外」として扱い、他の処理は続ける
- ルールファイルに書式エラーがあれば、起動時にファイル名と行番号を示して停止する

## 4. 自分ルール

### 初期ルール（利用者の 2026-11-05 住之江G1 の予想から言語化したもの）

| # | ルール | 必要なデータ |
|---|---|---|
| R1 | 1号艇の1コース勝率が高く、腕のある選手なら逃げ有力 | 選手のコース別成績、級別 |
| R2 | 風0m・水面が穏やかなら、逃げの信頼度アップ | 風速・波高 |
| R3 | 2コースの選手がその場で2コース勝率0なら、差しは消し | 選手の場別×コース別成績 |
| R4 | ダッシュが得意でも、内枠に入れば評価ダウン | コース別成績、進入 |
| R5 | モーター勝率が低い艇は、まくりに行っても伸びないので評価ダウン | モーター2連対率 |
| R6 | 3号艇がまくれば4号艇が展開をもらい、2〜1着候補になる | 展開シナリオ |
| R7 | 4号艇が開いたら5・6号艇がまくり差しで入る | 展開シナリオ |
| R8 | スタート展示で伸びている艇は評価アップ | スタート展示・展示タイム |

### ルールファイルの形式

`rules/common.yaml`（全場共通）と `rules/<場名>.yaml`（場ごと）に書く。同じ `id` のルールがある場合は、場ごとのファイルを優先する。

```yaml
- id: R1
  name: 1コース巧者は逃げ有力
  when:
    - boat: 1
      course_win_rate: ">= 0.70"
      class: [A1, A2]
  effect:
    scenario: { 逃げ: up_strong }

- id: R3
  name: 2コースの差しが無い選手は差し消し
  when:
    - boat: 2
      venue_course_win_rate: "== 0"
  effect:
    scenario: { 差し: down_strong }

- id: R8
  name: スタート展示で伸びた艇を評価アップ
  when:
    - boat: any
      st_exhibition_rank: "<= 2"
      exhibition_time_rank: "<= 2"
  effect:
    boat: { matched: { win: up_medium, top3: up_weak } }
```

- `when` は条件のリスト。すべて満たしたときに当てはまる（AND）。`boat: any` は条件を満たす艇があれば当てはまり、`matched` はその艇を指す
- `effect` の対象は `scenario`（展開シナリオの確率）か `boat`（艇の1着 `win` / 3着以内 `top3` の確率）
- 補正の強さは `up_strong` / `up_medium` / `up_weak` / `down_weak` / `down_medium` / `down_strong`。実際の値は設定ファイルの倍率で決める。初期値は強=2.0倍、中=1.5倍、弱=1.2倍（down は逆数）で、オッズ比（確率を「当たる/外れる」の比にした値）にかける
- R6・R7のような連鎖は `scenario` 側の定義に書く（例: 「まくり」シナリオ内の、3号艇がまくった場合の着順分布）。ルールはシナリオの確率を上げ下げする

### 確率の計算順

1. **ベース確率**: 級別・コース・勝率・モーター・展示から、各艇の1着確率を出す（多項ロジットモデル。初期の重みは過去データから推定する）
2. **シナリオ確率**: 各展開シナリオの確率と、シナリオごとの3連単の確率を求め、重み付きで合計する
3. **ルール補正**: 当てはまったルールの倍率をかけ、全体の合計が100%になるよう正規化する
4. 予想を出すたびに、当てはまったルールと、補正前後の確率を記録・表示する

## 5. 学習と進化

利用者の予想と結果を記録し、答え合わせを積み重ねて的中率・回収率を高める。これをアプリの中心機能とする。アプリはルールの中身を勝手に書き換えない。最終的な決定は利用者が行う。

### 5.1 予想ジャーナル（利用者の予想を記録する）

`boat bet` で、レースごとに利用者の予想を記録する。

```
boat bet 住之江 1R "1-456-全" --rules R1,R2,R3,R5,R6,R7 --confidence 4 --bought yes \
  --note "1の逃げ。2は2コース苦手、3はモーター弱い。4はスタート展示で伸び"
```

記録する項目:

- 買い目
- 根拠にしたルール（ID）と自由記述の理由
- 自信度（1〜5）
- 実際に買ったか（買った / 見送った）
- 記録した時点のオッズ
- 同じ時点のアプリの予想（確率・シグナル）

アプリで予想を出さなかったレースも、後から記録できる。

### 5.2 自動の答え合わせ（`boat review`）

結果が出たら、`boat review 住之江 1R` で振り返りを自動で作る（`watch` 実行中は結果の確定後に自動で作る）。

1. **利用者の予想**: 的中・不的中と、払戻金・収支
2. **アプリの予想**: 同じレースでの的中・不的中と、確率の当たり具合
3. **ルールごとの答え合わせ**: 各ルールの `effect` を「主張」として、結果と照らし合わせる

| ルールの主張 | 当たりの条件 |
|---|---|
| `scenario: {逃げ: up}` | 決まり手が「逃げ」 |
| `scenario: {差し: down}` | 決まり手が「差し」でない |
| `boat: {N: {win: up}}` | N号艇が1着 |
| `boat: {N: {win: down}}` | N号艇が1着でない |
| `boat: {N: {top3: up}}` | N号艇が3着以内 |
| `boat: {N: {top3: down}}` | N号艇が3着外 |

各ルールは「当たり / 外れ / 対象外」のどれかになる。シナリオ定義の中の連鎖（例: 3がまくれば4が2着）は、そのシナリオになったレースだけで判定する。

4. **修正候補**: ルールが外れたとき、実際の展開と着順から修正の方向を提案する。提案はルールごとに蓄積する
   - 例: 「R5（3号艇評価ダウン）：3号艇は1着ではないが2着。1着だけ下げ、3着以内は下げない形にすると今回は当たり」

#### 2026-11-05 住之江1R（結果 4-3-6、4のまくり）での出力例

| ルール | 結果 | 判定 |
|---|---|---|
| R1・R2（1号艇の逃げ） | 逃げ失敗 | 外れ |
| R8（スタート展示で伸びた4号艇をアップ） | 4号艇1着 | 当たり |
| R5（3号艇をダウン） | 3号艇2着 | 1着の主張は当たり、3着以内の主張は外れ |
| R6（3まくり → 4が展開をもらう） | 4が自分でまくった | 対象外（シナリオ違い）。逆の流れの候補を記録 |
| R7（4が開けば5・6が入る） | 6号艇3着 | 当たり |

### 5.3 ルールの強さを学習する

各ルールの補正の強さは、**場ごとに**、答え合わせの結果から学習する。

- 利用者が書いた強さ（強・中・弱）を出発点にする。データが少ないうちは、この値を約20レース分の重みとして扱う
- 答え合わせのたびに少しずつ更新する（ベイズ更新）。1レースの当たり外れで大きくは動かず、件数が増えるほど実績に近づく
- 表示例: 「R8 住之江：設定=中(1.5倍) → 学習後 1.9倍（該当42件、当たり67%）」
- 学習後の強さが、設定した方向と逆になった（上げるルールなのに実績では下げたほうが合う）場合は「見直し候補」として表示する。自動でルールを外したり、向きを変えたりはしない

### 5.4 あなたの得意・不得意の分析（`boat report me`）

利用者の予想、アプリの予想、両方を合わせた予想の3つについて、的中率と回収率を比べる。集計は次の切り口で行う。

- 場別
- 券種別
- 自信度別
- 展開別（あなたが予想した展開、実際の展開）
- 買ったレース／見送ったレース

これで、例えば「住之江の逃げ読みは的中率が高いが、まくり展開の読みは弱い」「自信度5のときは回収率が高い」といった傾向を見えるようにする。

**統合確率:** アプリの確率と利用者の予想を合わせた確率も出す。合わせる比率は、どちらが実際に当たっているかで場ごとに学習する。利用者の得意分野では利用者の予想を重く、苦手分野ではアプリの確率を重く扱う。

### 5.5 アプリ側の学習（自動）

- 毎日: 結果を取得し、その日の全予想（利用者・アプリ）の答え合わせをする
- 毎週（または `boat learn` 実行時）
  - 蓄積データでベースモデルを再学習する
  - ルールの強さと統合確率の比率を更新する
- キャリブレーション確認: 予想確率の区間ごとに実際の的中率を場別に集計し、ずれを補正する
- シグナルのしきい値の提案: 過去データ上で「的中率の下限を守りつつ回収率が最も高くなるしきい値」を計算して提案する。採用するかどうかは利用者が決める

### 5.6 ルールの成績表とルール候補（半自動）

- `boat rules report`: ルールごとに、場別の該当数・当たり率・回収率・学習後の強さ・蓄積された修正候補と、そのルールを外した場合との差を表示する
  - 該当が30件未満のルールは「様子見」と表示し、良し悪しは判定しない
- ルール候補の提案: アプリや利用者の予想と実績が繰り返しずれる条件を見つけ、ルール化を提案する
  - 例: 「住之江・4号艇がスタート展示1位のとき：まくり決着が予想12%に対し実績31%（n=48）。ルール化しますか？」
- 振り返りメモ（`boat memo`）を結果と一緒に保存し、ルールを作る材料にする
- ルールファイルは Git で管理し、変更した時期・理由と、変更前後の成績を比較できるようにする

### 5.7 学習しすぎを防ぐ決まり

- 新しい重みやルールは、学習に使っていない直近の期間で検証してから採用する。成績が悪化する変更は採用しない
- 件数が少ない条件（30件未満）の結果は、提案に使わない
- 採用・不採用の判断と、その時点の成績は履歴として残す

## 6. シグナル判定と買い目

### 買い目

1. **自動提案**: 券種（3連単・2連単・2連複・単勝）ごとに、確率の高い順に組み合わせを並べ、点数上限の範囲で組む
2. **利用者の買い目のチェック**: `boat check` で入力された買い目を評価する（例: `1-456-全` は 1着1、2着4・5・6、3着残り全部の12点）

### 計算式

- 合成オッズ = 1 ÷ Σ(1 / 各組み合わせのオッズ)
- 買い目の的中確率 = 各組み合わせの確率の合計
- 期待値 = 的中確率 × 合成オッズ × 安全率

### シグナル（数値はすべて `config.yaml` で変更できる）

| シグナル | 条件（初期値） |
|---|---|
| 🟢 堅い | 的中確率 ≥ 60% かつ 期待値 ≥ 1.0 |
| 🟡 妙味 | 期待値 ≥ 1.2 かつ 的中確率 ≥ 15% |
| ⚪ 見送り | 上記以外 |

- 両方に当てはまる場合は 🟢 を優先する
- 券種ごとに別のしきい値を設定できる
- しきい値を90%に設定することもできる（3連単ではほぼ出ない点に注意）

### オッズの扱い

- 判定は締切10分前・5分前・2分前の3回行い、シグナルが変わったら表示を更新する
- 締切直前のオッズの下落を見込み、安全率（初期値 0.9）をかける。安全率は蓄積データ（直前オッズと最終オッズの差）から調整する
- 金額配分は「同額買い」と「均等払い戻し（どれが当たっても払戻額がほぼ同じ）」の両方を表示する

## 7. 検証（バックテスト）の決まり

- そのレースの前に分かっていた情報だけを使う。レース後に更新される成績や結果は使わない（選手成績は、そのレースの時点のものを使う）
- 過去の検証では最終オッズしか手に入らないため、回収率は安全率をかけて表示し、実運用より良く出る可能性があることを明記する
- 学習用と検証用のデータは期間で分ける（例: 古い期間で学習し、新しい期間で検証する）

## 8. テスト方針

- **collector**: 取得したHTMLを保存しておき、テストではそれを使う。テスト中に実サイトへアクセスしない
- **model / scenario**: 120通りの確率の合計と、1着確率の合計がそれぞれ100%になること
- **rules**: R1〜R8それぞれについて、当てはまる例と当てはまらない例のテストを用意する。書式エラーの検出もテストする
- **signal**: 境界値のテスト（期待値ちょうど1.0、確率ちょうど60%など）、合成オッズの計算、買い目の展開（`1-456-全` → 12点）
- **backtest**: 同じデータと設定なら同じ結果になること。レース後の情報が混ざらないこと
- **review**: 2026-11-05 住之江1R（4-3-6、まくり）を固定データにして、5.2 の出力例と同じ判定になること
- **learning**: 1レースの結果ではルールの強さがほとんど動かないこと、件数が増えると実績に近づくこと、30件未満の条件が提案に使われないこと

## 9. 段階的な進め方

1. **第1段階（Windows PC）**: collector（公式サイト）→ DB → model → rules → signal → `predict` / `check` / `watch`、予想ジャーナル（`bet`）と答え合わせ（`review`）。記録はできるだけ早く始めたいので、ジャーナルは第1段階に入れる
2. **第2段階**: 過去データの収集 → backtest → ルールの成績表 → ルールの強さの学習・得意不得意の分析・統合確率
3. **第3段階**: ボートフロンティア連携、ルール候補の提案、キャリブレーション
4. **第4段階（必要なら）**: クラウドへ移す、通知、スマホ向け画面
